# Budget App — продуктовые решения и чекпоинты

Рабочий документ для перехода от текущего UI-прототипа к приложению для реальных пользователей.

Стратегический план деплоя и дальнейшего развития остаётся в `deployment-plan.md`. Этот файл фиксирует принятые решения, границы MVP и критерии готовности.

## 1. Принятые продуктовые решения

### Целевая аудитория первой версии

Первый пользователь — человек, который раньше системно не вёл бюджет, получает регулярный доход и хочет спокойно понять, куда уходят деньги и как распределить зарплату на месяц.

Первая версия не ориентируется на:

- семейные и совместные бюджеты;
- несколько пользователей в одном бюджете;
- сложную поддержку фриланса и нерегулярного дохода;
- банковскую синхронизацию;
- инвестиции и налоги;
- web-версию;
- Android.

Первый рынок — Ирландия, затем другие страны ЕС. Первая версия: английский язык и EUR. Другие языки и валюты закладываются позже.

### Главный мотив

Главный результат для пользователя:

> Понять, куда уходят деньги — и как распределять их грамотно.

Вторичные результаты:

1. Распределить доход по категориям.
2. Понимать, сколько осталось до следующей зарплаты.
3. Начать откладывать деньги.
4. Делать всё это без давления и чувства вины.

### Модель бюджета

Используется мягкая гибридная модель:

- можно начать только с фиксации расходов;
- планирование бюджета не является обязательным;
- плановая сумма у обычной категории может отсутствовать;
- после дохода приложение предлагает распределить деньги, но не блокирует пользователя;
- при перерасходе приложение мягко предлагает перераспределить деньги;
- приложение не запрещает дальнейшие расходы.

Бюджетный месяц начинается с 1-го числа по умолчанию, но пользователь может выбрать любую дату начала. Неиспользованные деньги автоматически переносятся на следующий месяц.

### Транзакции

Все транзакции вводятся пользователем вручную.

- одна транзакция относится ровно к одной категории;
- split transactions не входят в первую версию;
- форма добавления использует текущий интерфейс без самовольных изменений;
- поле `Add a note` остаётся необязательным свободным описанием;
- пользователь может вписать туда продавца или место траты;
- транзакции можно редактировать;
- транзакции можно удалять с подтверждением;
- после удаления доступен `Undo`;
- возврат денег вводится как доход с источником `Refund`;
- стартовая сумма может быть записана как `Starting balance` и не считается доходом.

### Категории

Новый пользователь получает готовый базовый набор категорий.

- категории можно переименовывать;
- категории можно архивировать;
- архивная категория исчезает из новых операций;
- старые транзакции продолжают ссылаться на архивную категорию;
- архив доступен отдельно;
- категорию можно восстановить;
- при переименовании новое имя показывается во всей истории;
- пользователь может создавать, редактировать и группировать собственные категории;
- доходы используют отдельные источники, которые можно создавать самостоятельно.

### Savings goals

Накопления реализуются как виртуальные savings-категории внутри общего баланса.

У savings-категории может быть:

- конкретная цель по сумме (`Goal by target`);
- цель по сумме и дате (`Goal by date`);
- отсутствие конечной цели — долгосрочное накопление.

`Goal by date` только рассчитывает необходимый взнос:

- пользователь задаёт сумму и дату;
- приложение учитывает уже накопленное;
- пользователь выбирает расчёт по неделям или месяцам;
- интерфейс показывает `Put aside €X per month/week`;
- приложение не переводит деньги;
- приложение не меняет бюджет автоматически;
- приложение не говорит, на чём пользователь должен экономить.

### Баланс и счета

В первой версии используется один общий баланс, воспринимаемый как единый `Cash`.

Не входят в MVP:

- отдельные банковские счета;
- Revolut/Bank of Ireland и другие интеграции;
- переводы между счетами;
- кредитные карты;
- банковский импорт.

Счета и банковская синхронизация — будущий этап.

## 2. Архитектура данных и переход в облако

### Local-first beta

Первая версия для TestFlight работает локально:

- основное локальное хранилище — SQLite через Expo;
- React state не является постоянным хранилищем;
- AsyncStorage используется только для небольших настроек;
- структура данных сразу проектируется с расчётом на перенос в Supabase;
- записи получают стабильные UUID/ID, даты создания и изменения;
- локальные данные не удаляются без явного действия пользователя.

### Supabase-обновление

После локальной TestFlight-беты выходит обновление с Supabase:

- пользователь создаёт аккаунт;
- основной вход — Sign in with Apple;
- альтернативный вход — email magic link;
- существующие локальные данные переносятся в облако;
- после успешного переноса облако становится единственным источником истины;
- локальная база остаётся только кешем для быстрого открытия и offline-работы;
- пользователь не выбирает между двумя независимыми аккаунтами.

При ошибке миграции:

- локальные данные сохраняются;
- приложение показывает ошибку;
- перенос можно повторить позже;
- локальные данные удаляются только после подтверждённого успешного переноса.

### Offline и синхронизация

После появления облачного режима:

- кеш можно просматривать без сети;
- новые записи можно создавать offline;
- изменения помещаются в очередь;
- приложение автоматически повторяет отправку;
- технические детали синхронизации не показываются постоянно;
- подробный статус находится в Settings;
- при ошибке пользователь не теряет локально сохранённую транзакцию.

Для конфликтов между устройствами:

- новые транзакции с разными ID сохраняются все;
- транзакции не должны теряться;
- для категорий и настроек действует правило «последнее изменение побеждает»;
- удаление синхронизируется через отдельный признак удаления, чтобы запись не воскресала.

## 3. Аутентификация, приватность и аналитика

### Аккаунт

В local-only beta аккаунт не нужен. Когда облачная возможность готова, приложение сразу предлагает создать аккаунт при первом запуске обновлённой версии. Переход можно временно пропустить, но предложение повторяется.

В публичной облачной версии аккаунт является основой backup и доступа с другого устройства.

### Управление данными

До публичного релиза должны быть готовы:

- Privacy Policy;
- Terms of Use;
- отдельный email поддержки;
- экспорт пользовательских данных минимум в CSV;
- удаление аккаунта и всех облачных данных.

В TestFlight экспорт можно отложить. JSON backup/import и PDF-отчёты не являются обязательными для первой публичной версии.

### Аналитика

Планируется собирать техническую и продуктовую аналитику по умолчанию, если это допустимо после проверки требований для выбранного рынка.

Можно собирать события:

- завершение onboarding;
- создание первой транзакции;
- создание категории;
- распределение дохода;
- создание savings goal;
- включение уведомлений;
- использование основных экранов;
- ошибки и crashes.

Не следует отправлять в продуктовую аналитику сырые финансовые данные без необходимости: суммы, заметки, продавцов и полный список транзакций.

Пользователь должен иметь возможность отключить продуктовую аналитику в Settings.

## 4. Уведомления и onboarding

### Onboarding

Onboarding короткий и пропускаемый.

Он постепенно предлагает:

1. указать стартовый баланс или начать с нуля;
2. выбрать/изменить стартовые категории;
3. добавить первый доход;
4. распределить доход по желанию.

Пользователь не блокируется из-за незавершённой настройки.

### Уведомления

Уведомления по умолчанию выключены. Пользователь сам может включить:

- ежедневное напоминание добавить расходы;
- еженедельное напоминание проверить бюджет;
- собственное время уведомления.

## 5. Монетизация

Публичный запуск планируется с подпиской:

- первый месяц бесплатно;
- месячный план;
- годовой план;
- окончательная цена определяется после TestFlight;
- предварительная модель для расчётов: €4.99/месяц и €39.99/год.

После trial базовый функционал остаётся доступным. Пользователь не теряет свои данные и не превращается в read-only архив.

Бесплатно:

- основные транзакции;
- категории и группы;
- базовый бюджет;
- общий баланс;
- backup и синхронизация;
- доступ с другого устройства.

Pro:

- расширенная аналитика;
- продвинутые savings goals;
- экспорт и расширенные отчёты;
- AI insights (Weekly Money Brief, ответы на вопросы вроде «могу ли я себе это позволить»).

Окончательная структура Pro и цена проверяются на реальных пользователях до публичного запуска.

## 6. Интерфейс

Текущий визуальный стиль и существующие экраны не менять самостоятельно.

Правило проекта:

> Любые изменения интерфейса выполняются только после явного указания пользователя, что именно изменить и как.

Разрешены только явно согласованные функциональные дополнения, необходимые для работы продукта, например:

- экран аккаунта;
- Settings;
- миграция в облако;
- состояния синхронизации;
- onboarding;
- экран подписки;
- Privacy Policy и Terms.

## 10. AI insights и персонализация под рынок (будущий этап)

Отдельный поздний этап, не привязанный к текущим чекпоинтам (0–5). Решение о конкретном
месте в дорожной карте принимается позже, ближе к моменту, когда до него дойдёт очередь.

### AI insights

Не чат ради чата — маленькие конкретные инсайты на основе реальных данных пользователя.
Через LLM-интеграцию (внешний AI API), а не только детерминированную логику.

Примеры:

- утренний `Weekly Money Brief`: «You spent €84 more than usual this week. Main reason:
  restaurants (+€61). You're still on track to save €500 this month.»;
- ответ на вопрос пользователя вроде «Can I afford a €1,500 MacBook next month?» с учётом
  его реальных трат, целей и emergency fund: «Yes, but buying it next month would reduce
  your emergency fund to €2,100. Waiting until October would let you buy it without
  touching your emergency fund.»

AI insights — платная (Pro) функциональность: LLM-запросы стоят денег на каждый вызов,
поэтому бесплатный тариф их не включает.

Требует отдельной проработки: стоимость LLM-запросов, задержка ответа, вопросы приватности
финансовых данных при отправке во внешний API.

### Ireland как первый рынок, страновая персонализация

Позиционирование: «The budgeting app built for Ireland» вместо обезличенного personal
finance app. Ирландия — тестовый рынок; если механика сработает, следующий рынок — UK,
затем условно Германия/Франция/Испания.

Архитектурная идея на будущее — `core` (budgeting, accounts, transactions, goals,
subscriptions, safe-to-spend, AI insights) отдельно от `country module` (валюта,
локальные налоги, локальные банки/мерчанты, терминология). Ireland-модуль первым:
EUR, Irish Income Tax, USC, PRSI, Irish Tax Credits, ирландские банки, ирландские
мерчанты/провайдеры счетов, ирландская терминология.

Решение зафиксировано как принцип, не как задача к исполнению: рефакторинг кода под
`core`/`country module` не начинается сейчас, Ireland/EUR остаются захардкожены как
сегодня — до того момента, как реально появится второй рынок.

Ирландский налоговый блок (Income Tax, USC, PRSI, Tax Credits) — отложен, не входит в
текущую работу. Что именно он должен считать (просто справочный gross→net калькулятор
или интеграция с бюджетом) — решается отдельно, когда до него дойдёт очередь.

UK намеренно не объединяется с Ireland на старте — рынок конкурентнее (Emma, Snoop,
Monzo, Starling с Open Banking), поэтому логично проверить механику сначала на Ireland.
